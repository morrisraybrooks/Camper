# project-jetson-voice-satellite

> Hey Jarvis" voice satellite on the Jetson (Brio webcam mic) whose spoken replies go nowhere; Bluetooth speaker is on the Pi

Found 2026-10-21 (built 2026-10-08, no notes were written then). Jetson user systemd units (`systemctl --user`, ~/.config/systemd/user, files in ~/camper_voice): voice-satellite (wyoming_satellite "Camper Jetson", :10700), voice-wakeword (openWakeWord, 127.0.0.1:10400, wake word **hey_jarvis**), voice-whisper (faster-whisper base-int8 CPU, :10300 = HA `stt.faster_whisper`), voice-piper (:10200 = HA `tts.piper`). HA entity `assist_satellite.camper_jetson`; its pipeline select is "Camper Brain (Local)". Mic = Logitech Brio 100 webcam (`plughw:CARD=B100,DEV=0`).

**Gap (fixed 2026-10-21, see update below):** `--snd-command paplay` plays replies and chimes on the Jetson's default sink `alsa_output.platform-sound.analog-stereo`, which has no speaker attached, so replies are silent. The Bluetooth speaker (ECOXGEAR, see [[project-camper-stereo-bluetooth]]) is connected to the **Pi**, not the Jetson; the Jetson has its own BT radio but nothing is paired to it. No HA automation forwards satellite replies to `media_player.camper_stereo`. Only one test recording exists (2026-10-08).

**Alternative not built (offered 2026-10-21):** a wyoming_satellite `--event-uri` handler on the Jetson that takes the reply text from `synthesize` events and calls `tts.speak` on media_player.camper_stereo via HA. Related: [[jetson-ai-agent]].

**2026-10-21 voice testing lessons:**
- Never put "Hey Jarvis" in an announce/TTS message: the mic hears the speaker and the satellite wakes itself. A second wake cancels the first run mid-LLM, and HA then got stuck in "listening" (out of sync with the satellite). Fix: reload the wyoming entry 01M4EPF80TH5KHC5SPGSP8P7XG (POST /core/api/config/config_entries/entry/<id>/reload); restarting the satellite service alone did not fix it.
- The user didn't hear the beep: the BT sink was SUSPENDED and the ~0.24 s awake.wav was lost while A2DP woke up. The user then waited silently, and Whisper hallucinated a list of entity names from 15 s of silence. Fix: `~/.config/wireplumber/bluetooth.lua.d/51-bluez-no-suspend.lua` (session.suspend-timeout-seconds=0 for bluez_output.*), plus speaker-reconnect.sh plays 0.2 s of silence when the sink is SUSPENDED (after a reconnect or wireplumber restart). User confirmed hearing the beeps afterwards.
- The first LLM request after a reboot takes ~16 s (~6k-token prompt, cold cache); later ones are faster. Warm it up with `assist_pipeline/run` start_stage=intent on pipeline 01m4epfd9mwjv6nsk3981evfwf. Pipeline debug: `assist_pipeline/pipeline_debug/list|get`.

2026-10-23 stereo fix (final): "Turn off the stereo" had made the LLM call HassTurnOff on the stereo and the Roku TV. media_player.camper_stereo (vlc_telnet) has NO turn_off, so that call did nothing, but the TV really went off. What fixed it:
- Renamed camper_stereo in the entity registry to "Speaker". Kept the word "stereo" out of its names, because with prefer-local on, HA's built-in matcher would catch "turn off the stereo" and fail with ServiceNotSupported.
- Added a line to the llama_cpp prompt (entry 01M43ME5M6SSHE6M1MSJ846W0B, changed via the subentry reconfigure flow): stereo/music = "Speaker"; use HassMediaPause name "Speaker"; never turn off the TV unless "TV" is said; always call the tool, never answer from memory.
- Text test passed: stereo paused, TV stayed on.
- GOTCHA: setting entity aliases to [] wipes aliases_v2 [None] (None = the computed real name). The entity then shows as names '' to Assist and the LLM can't target it. Always keep None in the list, e.g. aliases [None, "x"].
