# project-camper-easytouch

> Camper's Micro-Air EasyTouch thermostat integration on HA Pi — fixed wrong BLE MAC and turn_off bug

The camper's climate/thermostat setup lives on [[project_pi_haos]] (Pi at 192.168.0.168, Home Assistant OS), dashboard file `/homeassistant/dashboards/camper.yaml`, Climate view (`path: climate`).

Thermostat: Micro-Air EasyTouch, integration `custom_components/micro_air_easytouch` (HACS custom component), config entry title/unique_id is the Bluetooth MAC address, e.g. `climate.easytouch_31_7f_98_77_f8_d1_easytouch_climate`.

**Issue found & fixed 2026-09-12:** the integration was configured with the wrong BLE MAC (`31:7F:98:77:F8:D1`) — the real thermostat broadcasts as `F4:2D:C9:59:E5:52` (found via `bluetoothctl scan on` on the Pi). Corrected the MAC in `core.config_entries`, `core.device_registry`, and `core.entity_registry` (entity_ids/dashboard refs were left as-is — only the internal unique_id/address fields changed), then `docker restart homeassistant`. That left an empty ghost device "EasyTouch 31:7F:98:77:F8:D1" (0 entities); removed from core.device_registry 2026-10-08 with HA stopped (the integration has no device-delete support). Backup `core.device_registry.bak-preclaude-rmghostezt-20261008-163849`. The only device now is "EasyTouch F4:2D:C9:59:E5:52"; entity_ids still say 31_7f_98… on purpose. Also patched `climate.py` `_attr_supported_features` to add `ClimateEntityFeature.TURN_ON`/`TURN_OFF` (the mushroom-climate-card's power-icon tap calls `climate.turn_off`, which the integration didn't declare support for, causing a WS error) and added an explicit `hvac_modes` list to the mushroom-climate-card in the dashboard so mode icons (off/cool/heat/auto/dry/fan) show directly instead of relying on the broken toggle.

Dashboard Climate view now has: weather readings card, EasyTouch thermostat card (temp control + mode row), Return Air temp sensor card, Reboot button card, and a connection-status card.

**"AC stops blowing cold but still runs" investigated 2026-09-18:** root cause was the user's phone running the Micro-Air app connected via Bluetooth at the same time as HA — the EasyTouch only accepts one BLE client, so the phone holding the connection makes HA's commands fail/partially land. Confirmed via live debug-logged test: with the phone connected, HA's BLE connection to the thermostat dropped out entirely for 5+ min (`No backend with an available connection slot`); with the phone disconnected, the same fan/mode changes landed cleanly with zero errors. Fix is behavioral: don't have the Micro-Air app connected while also controlling it from HA. Not a bug in the integration code.

**Gotcha: the climate integration's poll loop can silently wedge.** During this session it stopped polling entirely for ~13 minutes (no debug log output at all, not even errors) after heavy back-to-back BLE command testing — almost certainly `parser.py`'s shared `asyncio.Lock` got stuck on a hung BLE operation, blocking every future poll and command silently (no exception, no timeout). Symptom: dashboard looks frozen/stale, fan/mode button clicks and number.set_value calls appear to do nothing, `states.<entity>.last_updated` stops advancing. Fix: `sudo docker restart homeassistant` on the Pi. Diagnose by checking `last_updated` via Developer Tools → Template before assuming a write failed.

**Gotcha: HA's Developer Tools → Actions YAML editor (CodeMirror) auto-indents on Enter**, which corrupts multi-line YAML typed via automated "type a whole string with embedded newlines" input — a `data:` block can silently end up nested one level too deep (e.g. under `target:`), producing a schema error that's easy to miss if you don't re-check the YAML after typing. Symptom looked identical to a real device write failure (no error, just silently no-op) until switching to UI mode surfaced "not a valid option at 'sequence[0].target.data'". Workaround: type line-by-line as separate actions, pressing `shift+Home` after each `Return` to strip the auto-inserted indent before typing the next line — or just use the entity's more-info dialog (plain number input, no YAML) for simple value changes instead of Developer Tools.

**Two real mushroom/card-mod gotchas found while validating the recolor (both fixed, both apply to any future edits on this dashboard):**
1. `custom:mushroom-entity-card`'s name/value text does **not** reliably respond to `ha-card .primary { color: X }` / `ha-card .secondary { color: Y }` class selectors — it reads the `--primary-text-color`/`--secondary-text-color` CSS custom properties instead. The class-selector approach silently no-ops (text falls back to a pale default), invisible against the old dark theme but glaring against light backgrounds. Fix applied dashboard-wide: every `ha-card { ... }` card_mod block now also sets `--primary-text-color: #2B2A28 !important; --secondary-text-color: #6B6558 !important;` directly. (`custom:mushroom-template-card`, used for the mode/fan buttons, is fine with `[slot=primary]`/`[slot=secondary]` — that one *does* work.)
2. A single `custom:stack-in-card` with too many deeply-nested children (~13, the old THERMOSTAT card mixing mode buttons + fan buttons + status + alerts + humidity all in one stack) intermittently fails to apply card_mod styling to inner cards on load — they render as unstyled dark boxes instead of picking up the theme, a race that's invisible against a dark theme (unstyled dark still looks dark) but obvious against light. Fix: split it into 4 smaller stacks (Thermostat controls / Status / Temperature Alerts / Humidity) — keep any one `stack-in-card` to a handful of children, not a dozen.
