# project-camper-stereo-bluetooth

> Furrion DV3100 stereo as the HA speaker over Pi Bluetooth; the hands-free (HFP) fix that made it work, and its reconnect behavior

Furrion DV3100 camper stereo (BT name DV3100-148974, MAC 00:13:04:02:45:EE) is HA's speaker `media_player.camper_stereo`. Path: VLC add-on → hassio_audio PulseAudio → bluez A2DP sink on the Pi 4's built-in BT. See [[project_pi_haos]].

**What fixed it (2026-10-13, user confirmed "that worked"):** hassio_audio's default `module-bluetooth-discover` registers HSP/HFP "Handsfree Audio Gateway". The stereo is phone-oriented, so it tries hands-free setup. That fails (bluetoothd: "Unable to get io data for Hands-Free Voice gateway"), and a couple of minutes later the stereo drops the Pi. Earlier, Pi-started connections streamed with no sound. Fix: in hassio_audio run `pactl unload-module module-bluetooth-discover; pactl load-module module-bluez5-discover headset=ofono`, so only A2DP is offered and there's no HFP. **Made permanent (2026-10-13):** HAOS /etc is read-only, so there are no custom systemd units. Rule `/etc/udev/rules.d/99-camper-stereo-nohfp.rules` (a persistent bind mount) fires on bluetooth DEVTYPE==host add, which happens every boot, and runs `systemd-run --unit=camper-stereo-nohfp /bin/sh /mnt/data/camper-stereo/nohfp.sh`. That script loops every 30 s and re-applies headset=ofono if hassio_audio lost it. `udevadm test` confirmed the rule matches hci0. A real reboot test hasn't been done yet, so check `systemctl is-active camper-stereo-nohfp` after the next reboot. To remove: stop the unit and rm the rule and script.

**Behavior learned:**
- The pairing persists across Pi reboots.
- The stereo auto-connects to the Pi when the stereo is powered on. That's the reliable way to connect.
- Once the stereo drops a device, it ignores Pi connect attempts (br-connection-page-timeout) until it's power-cycled.
- I also set host `hciconfig hci0 pageto 32768` (20 s). That isn't persistent either, and it's unclear whether it mattered.
- After connecting, set the default sink to `bluez_sink.00_13_04_02_45_EE.a2dp_sink` if needed. VLC volume once came back as 0 after a reboot; it was set to 0.7.

**Don't:** the user rejected switching HA's Bluetooth adapter (entry 01K9HWJN7T13CNHXHYWRSAKA0R) to passive scanning, so leave the scan mode alone. The user is physically limited ("im crippled"), so minimize asking them to walk to the stereo and power-cycle it. Their wireless Logitech mouse and keyboard on the ODROID got glitchy during heavy BT work, possibly 2.4 GHz interference from a USB3 PNY flash drive next to the receiver.

**Why:** the user fought this for an hour and wants it to just work.
**How to apply:** if the stereo is silent, first check `hcitool con` on the host, the bluez sink in hassio_audio, and whether the headset=ofono module is loaded. Re-apply the fix before asking the user to do anything.

**Playing YouTube on the stereo (2026-10-20, worked):** the ODROID has no Bluetooth, so music has to go through HA. Get the audio URL with `~/.local/bin/yt-dlp --cookies-from-browser chrome -f bestaudio -g <yt url>` (without cookies YouTube says "Sign in to confirm you're not a bot"). Then call `media_player.play_media` on `media_player.camper_stereo` with content type music, through `sudo docker exec -i app_core_configurator sh` on the Pi (the Pi's docker needs sudo). The URL is tied to the camper's public IP, which the Pi shares, so it works. The power-cycle reconnect happened within about 20 s.
**Crackle fix (2026-10-20):** HA volume for camper_stereo maps to roughly 2x in VLC/PulseAudio (0.7 became 137%, which clips). Keep HA volume ≤0.5 (≈98%) and let the user turn up the stereo knob. The Pi is on Ethernet with Wi-Fi off, so there's no BT/Wi-Fi coexistence issue. The codec is SBC.
